# Lessons: wrong assumptions found along the way

A log of assumptions that turned out false, so the context never disappears. Append, never delete; mark an entry superseded when a later one replaces it. One entry per assumption, newest first within a batch.

Rule (CLAUDE.md "How work is run"): whoever discovers the mistake writes the entry in the same commit as the fix; an entry that changes what the system should do is written by the orchestrating model and also lands in SPEC and SCENARIOS. Format: **Assumed** · **True** · **Found by** · **Changed** (SPEC §, code, scenario).

## Data sources

- **2026-11-06 · Forever installs into `_classic_beta_`, and the Classic folders are fallbacks.** Assumed (SPEC §1, §3.7.3): the release would keep the beta's folder, and `_classic_`, `_classic_era_` and `_anniversary_` were reasonable candidates. True: the release installs into `_forever_` (flavor `wowf` in `.flavor.info`), and the Classic folders are other games: on the user's Mac they hold addons, so the old rule (the first candidate with `Interface/AddOns`) could have installed AHProfit into Cataclysm Classic. A fresh install also has no `Interface/AddOns` until an addon is installed, so setup refused it. Found by the user installing the release. Changed: `WOW_NAMES` (`_forever_`, `_classic_beta_`), both Windows roots, detection by flavor first, setup creating `Interface/AddOns` (SPEC §1, §3.7.3, §6 items 10 and 20; DR6).
- **2026-11-06 · A Forever auction house belongs to a ruleset.** Assumed (the launch-day notes, SPEC §2.4 draft): the route `/ruleset/{id}/auctions/{house}` meant each ruleset has its own houses, with one duplicate as a launch-day quirk. True: the ruleset in the URL is ignored; each of the four Horde houses with data answers the same auction list under all four rulesets, and they are four separate markets. Found by recording every Horde house under every ruleset (`tools/record_blizzard.py`, M28). Changed: SPEC §2.4 (the house id is the market) and §6 item 23; the PvE house is chosen by a marker auction, not by the route.
- **2026-11-06 · Forever has no Blizzard auction house API.** Assumed (SPEC §1): prices could only come from players' scans (AHF, AHledger), so every source was community data with gaps. True: Blizzard's Game Data API serves Forever's auction houses under a ruleset (`/data/wow/ruleset/{id}/auctions/{house}`, namespace `dynamic-forever-us`), refreshed about hourly, every auction with an id, quantity, asking price and time-left band; unofficial and undocumented, probed on launch day. Found by the user pasting community notes. Changed: SPEC §1, the new §2.4, M28–M35 (`docs/plans/blizzard-cloud.md`): a cloud collector and analyzer, the published summary, AHF and AHledger retired at M34.
- **2026-10-22 · AHledger's market ids need mapping.** Assumed its ids would differ from ours. True: `/v1/markets` uses our exact ids (`forever.pvp.horde.us`); only its web pages and the price table header use slashes. Found by calling the endpoint. Changed: `[sources].addresses.ahledger` defaults to the market id (SPEC §3.6).
- **2026-11-01 · AHledger's public surface is just the price table.** Assumed per-item history needed a key or didn't exist. True: `/v1/prices/<market>/<id>` is keyless and gives hourly buckets for 7 days and daily for 90. Found by the user pasting the developer docs. Changed: M21 backfill (SPEC §2.3).
- **2026-10-22 · Installing a second scanning addon adds scan data.** Assumed AHledger's or Auctionator's scans would be new data. True: Forever's full listing is one server answer shared by every addon; AHProfit already reads it whoever asked. Found by reading `Scan/Replicate.lua` and AHledger's source. Changed: nothing in code; the decision not to read other addons' SavedVariables (SPEC §2.3).
- **2026-10-21 · AHF would come back.** AHSync kept retrying AHF hour files (137 failures) and the plan excluded every candidate as "Forecast too stale" while treating AHF as primary. True: the feed has published nothing for this market since 2026-10-09 and the user's own scan was the only live source. Found by the user asking why the Portfolio showed only holds. Changed: `primary` defaults to AHledger with a fallback to the first enabled source (SPEC §3.6, SRC10).
- **2026-10-17 · Forever's time-left bands are retail's 0–3.** True: 1 short … 4 very long, as Classic; AHF's Premium books arrive shifted by one. Found in game and against AHF books. Changed: SPEC §2.1 books row, §4.2 reading, A12.

## Engine and plan

- **2026-11-09 · An item missing from a cloud snapshot only needed its age fixed.** Assumed (BZ50): the staleness gate was the only thing reading an unlisted item's kept price, so making it "as old as the snapshot" was enough. True: the summary also keeps the item's last book, and the plan bought from it: SD11's decoy craft bought a reagent gone since day 0 at every login, which the 24 h gate had ended after a day before BZ50. Selling your stock and buying from the book are different questions. Found by: Opus running MS4b-2 (SD11). Changed: `contract.buying_view` on the plan's and the Craft and Disenchant pages' inputs; SPEC §3.4D.6; BZ51.

- **2026-11-09 · A post is one auction, so it either sells or expires.** Assumed (SPEC §3.3.3, §3.4.1): a mail resolves a post of exactly its quantity, and the sell record counts each post as sold or expired. True: Forever's commodities sell in parts, a sold mail for each buyer's units and one expired mail for the rest, so a commodity post almost never resolved (8 of 11 Silk posts in the simulator's SD5 world), the one that did counted as an expiry however much of it sold, and the record (1 sold, 2 expired) cut Silk's chance from 85% to 63%, under the flip margin, for 30 days; positions also took a whole post as sold at its first sold mail. Found by: Opus building SD5's world (MS4b). Two things can't be undone on an existing database: a post the old rule resolved with an unrelated mail of the same quantity keeps that outcome, and its own mail may now attach to another open post; payouts realized before the upgrade keep the deposit they were realized with (0 for a mail that wasn't linked). Changed: `tracking.resolve_posts` by units, `posts.sold_units` and `returned_units` (schema 29), `sell_record` counting each post's share sold, History summing a post's payouts, positions moving each sold mail's units; SPEC §3.3.3, §3.4.1; T25, T26, O19, PO15.

- **2026-11-09 · An item missing from the auction house has a stale price.** Assumed (SPEC §3.4D.6): "Forecast too stale" could read the age of an item's last listing. True: on a cloud market every snapshot is the whole auction house, so an item absent from a fresh one is sold out, not unseen; a thin item that buyers clear within the hour (SD15's Mageweave: absent from 78% of snapshots, gaps up to 35 h) aged past 24 h between listings and the plan held all 300 units. Found by: Opus tracing SD15 (MS4a's finding). Changed: `recommend.portfolio.price_ages(prices_ms=…)`, SPEC §3.4D.6, BZ50.
- **2026-11-09 · The liquidity cap counted only others and one window at a time.** Assumed (SPEC §3.4 Liquidity): `units_on_ah` is others' supply, and each window's cap stands alone. True: a cloud book names no seller, so our own auctions were counted as others' and raised our cap; and posting now beside a window whose post time had passed were two caps for auctions listed at the same moment, on top of what we already had up (SD15: 12 units of ours against a cap of 4, with nobody else listing). Found by: Opus tracing SD15's breaches. Changed: `plan.capacity_groups`, `SellFacts.own_listed`, `recommend.plan.own_listed`, SPEC §3.4 Liquidity, R31, R32.
- **2026-11-09 · FM5 guards against a one-snapshot dip.** Assumed (SD29, MS4a's triage): a 20% dip seen by one snapshot is FM5's to ignore, and the engine read cancelled auctions as sales. True: FM5 flags only a price below 10% of `p10_30` or above `p90_30` by far, so 131 c against 164 c is a normal price; the sales rate was the same with and without the dip; the plan undercuts the dip's price (seed 1) or, through the 600 units it adds to supply, dumps its stock now (seed 2). The simulated sellers also copy the dip, so it leaves real cheaper auctions behind for hours. Found by: Opus tracing SD29. Changed: SD29 measures the login that sees the dip (13:00) and reports the evening one; the guard is the confirmed floor (scheduled for the sold-price fix, plan §1.40), not an FM5 change.

- **2026-10-20 · Found stock's profit belongs to committed capital.** The section A footer counted found stock's estimated net over a committed capital it never used, printing +391%. True: profit % on capital excludes rows that cost nothing, the same rule the funded lists use. Found by reading the W1 snapshot diff at review. Changed: `portfolio_view` footer and note, SPEC §3.4D.8, D73/A79/PF22.
- **2026-10-22 · Every hour-of-week slot has weeks of data.** The heatmap reading line printed a fallback ratio (0.99) for a slot with no data while its cell said "no data". Found by rendering the real dashboard headless. Changed: `gathering_history.reading` says "slot: no data", GA31.
- **2026-10-19 · A thin item can have a sell window.** Items with under 24 closes got windows and premiums from noise (0-week slots, 35× ratios). Found on the live database. Changed: W16, TT22, TT23, PP4, R28 (SPEC §3.3.4, §3.4D).
- **2026-10-19 · Partial commodity fills are sales.** Group diffs by (key, price) counted a stack partly sold as fully sold, doubling market-wide sales. Found on a 28-minute live scan pair. Changed: unit-level diff, VOLUME_METHOD_VERSION 4, V42/V43.
- **2026-11-08 · A cancelled auction returns its deposit.** Assumed (SPEC §3.4.1, D68, positions' replay): a cancel realized 0 and only an expiry lost the deposit. True: the AH keeps the deposit of a cancelled auction as well. Found by: the user's in-game check while planning the market simulator. Changed: a cancelled post realizes −deposit (T24), a position loses it (PO14), History's Deposits lost counts cancels (D48).
- **2026-11-08 · The deposit is a Classic-style share of the vendor price per duration.** Assumed (SPEC §3.4 Fees, `fees.DEPOSIT_BP`, seeded and marked unverified): 1.25%, 5% and 15% of the vendor value for 2, 8 and 24 h, floored, with no minimum. True: 5%, 20% and 60%, floored, and at least 1 s an auction, so a cheap post always pays 1 s and a 24 h post of anything else pays four times the seed. Found by: the user's in-game readings (a Healing Potion, vendor 75 c, took 1 s at every duration; an Oiled Blunderbuss, vendor 11 s 73 c, 2 s 34 c for 8 h), while planning the market simulator. Changed: `fees.py` and `Fees.lua` (P27), gathering's deposit a unit (an unknown vendor price now pays the minimum too), the scenario rows whose numbers carried a deposit, the whole-plan snapshot (same actions, the week 61 c lower).
- **2026-11-08 · Every sale shows up between two snapshots.** Assumed (SPEC §2.4 Auction lifetimes): following each auction id from first sight to its end observes most of what is sold. True: units bought before a listing's first snapshot are never seen, whether the whole listing (posted and bought out between two refreshes) or part of it (bought down before it was first listed in a snapshot): in the simulator's first steady market (MS1, hourly refreshes) 9–17% of all units sold, more for a busier item. Found by: the market simulator's truth log against `engine.volume.lifetimes`. Changed: the sales before a commodity listing's first snapshot are estimated from its first observed gap (BZ45, `engine/unseen.py`; the user chose this estimate on 2026-11-08 after a comparison across market shapes); listings bought out whole before they are seen stay unseen, so SM1 stays pending until fitted seller behaviour (MS2) says how often that happens.
- **2026-11-08 · The overlap split between sold and expired is rare.** Assumed (SPEC §2.4 item 4): with an hourly snapshot the expiry window is usually under an hour, so a vanish gap rarely overlaps it. True: an auction's expiry window is its posting gap (about an hour), so nearly every auction that expires vanishes in a gap that overlaps its window and is split by the overlapping fraction, which ignores how likely it was to sell at all: in MS1's market 147 of Linen's 3,913 expired units (3.8%) were counted sold, partly offsetting the unseen sales above. Found by: the market simulator, auction by auction against its truth. Changed: selling and expiring compete in the split, weighed by the item's early-leave rate (BZ44, `engine/expiry.py`, `ID_METHOD_VERSION` 7); across six simulated market shapes the net error fell from +3–6% of units sold to +1–2%.
- **2026-11-08 · The undercut share is measured at first sight as it was at posting.** Assumed: SPEC §3.3.2 measures `u(p)` from each new listing's position against the cheapest other price in the snapshot that first saw it, as a stand-in for its position when posted. True: in SM2's undercut war the engine reads 0.03–0.07 at the post-now position against a true 0.13–0.25; a listing posted under the floor is bought before any snapshot, or by its first snapshot the floor has moved under it (0.10–0.22 among the seen listings alone), so `u` is under-read and the chance it feeds over-read where undercutting is common. Found by: MS2's SM2. Changed: nothing yet; recorded (plan §1.30) for M33b.
- **2026-11-09 · A flip buys whole auctions.** Assumed: `engine/flips.py` bought other sellers' auctions whole, as gear is bought. True: Forever lets a buyer take any number of a commodity auction's units, and on the 31 real hours 147 commodity auctions in one snapshot held 1,000 units or more (up to 10,000); one bigger than every selling window's capacity was never a candidate. Found by: the market simulator's MS4 (a 3,000-unit Silk dump at 45% of `med7`). Changed: a commodity is bought by the unit, cheapest first across auctions, in steps of the reference stack (a step may end inside an auction or span several), each a batch the optimizer funds within the risk budget and the character's gold (R30).

## Tooling and process

- **2026-11-10 · A `{ }` comment in an Inno Setup `[Code]` section can say anything.** Assumed: Pascal comments are opaque to the compiler. True: ISCC splits the script into sections line by line before Pascal parses it, so a comment line starting with `[InstallDelete]` stopped the build ("Invalid section tag", line 97). Found by: the PR build job for FM82. Changed: the comment reworded; FM82's test fails on any `[Code]` line that starts with `[`.
- **2026-11-10 · Stopping AHSync frees every file in its install folder.** Assumed (M26, SPEC §3.7.12): the installer only had to quit `AHSync.exe` before replacing files. True: since the MCP batch the folder also holds `ahsync-mcp.exe`, which Claude starts and keeps running for its whole session. The 0.1.15 silent update deleted `_internal` (`[InstallDelete]`), could not replace the running bridge ("Access is denied"), aborted under `/SUPPRESSMSGBOXES`, and Inno Setup's rollback restores only what it copied, not what `[InstallDelete]` removed: 14 DLLs the bridge held were left, and AHSync failed with "Failed to start embedded python interpreter" (`No module named 'encodings'`). Found by: the user's AHSync failing to start; the setup log in `%TEMP%`. Changed: `packaging/windows/ahsync.iss` refuses in `PrepareToInstall` and `InitializeUninstall` while the bridge runs, before anything is touched (SPEC §3.7.12, FM82). An install already broken this way is repaired by quitting Claude and running the downloaded installer from `<data>/updates/` again.
- **2026-11-09 · A steady price slide makes the plan over-pay.** Assumed (SD32's row, the plan's §3): buying into a 30-day fall fails by design, the post-price clamps sitting above tomorrow's price. True: a 2%-a-day slide keeps the cheapest price only 6–8% under the 7-day median and the 10th percentile, so no flip clears the 20% margin and the plan buys nothing (seeds 1 and 2); SD32 is "not exercised" in that world. Found by: Opus running MS4b-1. Changed: SD32's row and plan §1.43; a drop large enough to open the margin is SD5's and SD28's.

- **2026-11-09 · A decision row can run on the daily summaries.** Assumed (MS4a): SD15 ran without the hourly mode, to keep it fast. True: production plans with a new summary every hour, and on daily ones a 10:00 login reads prices up to 29 h old, so the row measured the cadence, not the plan (8 snapshots listing our stock instead of 40). Found by: Opus tracing SD15. Changed: SD15 runs hourly; a row about selling pace or reaction runs on production's cadence (`tools/sim/decision.py`).

- **2026-10-20 · A bench over 120 s means a code regression.** Measured 125–137 s across M13 and M14 and suspected the new code. True: the unchanged M13 code measured the same on the same day; the next day both read 100 s. The machine's load moves the bench by 30%. Found by timing HEAD and the branch back to back. Changed: compare against HEAD on the same machine before blaming a change (plan §2.3).
- **2026-10-19 · A worktree can be removed from anywhere.** Removing a worktree while the shell's cwd was inside it failed and re-rooted the shell. True: leave the main tree's cwd alone and use `git -C`; a worktree lock from a finished agent needs `remove --force --force`. Changed: CLAUDE.md "How work is run".
- **2026-11-01 · The worktree path is case-insensitive to the harness.** A lowercase drive letter in the working directory made the isolation worktree refuse to start. True: the harness compares paths textually. Changed: nothing in the repo; noted here so the next failure is recognised.
- **2026-10-22 · String tests prove the dashboard renders.** Three milestones changed `index.html` on JS string tests alone; a headless render then found a real inconsistency. Changed: a headless render is part of every dashboard milestone's verification (plan §2.3).
- **2026-11-01 · AHledger's price table arrives as plain text.** M19's fake transport served it uncompressed, and every test passed. True: our client sends `Accept-Encoding: gzip`, so api.ahledger.com answers with `content-encoding: gzip`. The first live poll after M19 logged "the price table's format changed; nothing stored", and no AHledger row was ever written. Found by checking the live log after the batch. Changed: `parse_pricetable` decompresses a gzip body (SRC17). Lesson: a new remote source's verification includes one live call through the real client before its milestone closes.
- **2026-11-01 · No table yet means nothing to backfill today.** The backfill marked a market "done for the day" when no price table was stored. True: a later poll can store the first table, for example after AHledger was unreachable at start, and the backfill then waited until the next day. Found by reading the code while checking the first live run. That run was fine: its first poll came before the first tick, and the run looked stalled only because it writes progress every 100 items, about once a minute. Changed: no table means "ask again next tick" (SRC18).
- **2026-11-01 · A price table's `updated` is when it was scanned.** Every table was assumed to be stamped with its scan time, so its hour was recorded as observed. True: AHledger stamps an empty table (a market nobody has scanned) with its publish time. An empty table would have recorded every poll's hour as observed, so the coverage card would credit AHledger for those hours and the backfill would see no gap. Found by listing every market's table header live. Changed: only a table with a priced row records an observed hour (SRC19); SPEC §2.3, §6 item 19.
- **2026-11-01 · `run()` refuses a missing `config.toml`.** The packaging plan (22.5) expected the shell, until setup mode exists, to leave a missing config to `run()`'s own refusal. True: `load_config` reads a missing file as all defaults (SPEC §3.6), so `run()` would sync the default market against the default WoW folder. Found by Opus writing M22's shell tests (a fake transport of `None` was called). Changed: the shell refuses a missing config itself until M23 serves setup there (SPEC §3.7.1); `python -m ahsync` keeps its defaults.
- **2026-11-01 · A port that binds again proves the dashboard stopped.** `test_start_serves_the_dashboard_during_the_steady_state_and_stops_it` checked the stop with a plain `bind()`, which passed on Windows. True: on macOS the request's closed connection leaves a TIME_WAIT socket on the port, and a `bind()` without `SO_REUSEADDR` fails with `EADDRINUSE` (errno 48) although the server has stopped; the dashboard itself binds with `SO_REUSEADDR`, so a real restart is unaffected. Found by the first macOS CI run (M22). Changed: the test asserts the connection is refused and that a `ThreadingHTTPServer` binds the port, as the next start does; nothing in `ahsync/` changed.
- **2026-11-01 · The Status topic `api_key` was free for setup's line.** M23 first stored `api_key_not_saved` under `api_key` and cleared it at every start with a key. True: FM25's `key_rejected` already lives there, so a start would have erased a still-valid "API key rejected" warning. Found by the independent review of M23. Changed: setup's line uses `api_key_setup` (SPEC §3.7.4).
- **2026-11-02 · Turning a LaunchAgent off with `launchctl bootout` is harmless.** The spec loaded the agent with `bootstrap` and removed it with `bootout`. True: `bootout` stops the job's running process, and after a login start that process is AHSync itself, so the Start at login toggle would have quit the app it sits in (and a self-heal that reloads the agent would quit it at every start). Found by Opus while building M24's writers. Changed: the plist file alone, no `launchctl` (SPEC §3.7.5, DR10, FM51; the user's call).
- **2026-11-02 · Cancelling the window's `closing` event only stops the user's close.** M24's close handler hid the window and returned False. True: pywebview's `destroy()` closes the form through the same event, so Quit and the stop file left AHSync running with no window. Found by Opus in the end-to-end run from source. Changed: after Quit the close goes through (`WindowState.quitting`, a DR29 check).
- **2026-11-02 · `sys.executable` is what a login entry should start.** True only for a build: from source it is `python.exe`, and `"python.exe" --autostart` starts nothing. Found by Opus in the end-to-end run. Changed: from source the entry is `pythonw.exe` with the path of `ahsync_app/__main__.py` (SPEC §3.7.1).
- **2026-11-02 · Any callable is a pystray menu action.** True: pystray counts a lambda's parameters, defaults included, and rejects more than two, so the menu raised when first built. Found by Opus in the end-to-end run. Changed: the adapter builds each handler in a small function; a test builds the items with the real pystray when it is installed.
- **2026-11-02 · Opening the database for one Status line is harmless.** M24's shell wrote its Status lines through `Database.open` while `run()` was running. True: `Database.open` migrates and drops every staging table, so a toggle during a full refresh would have published an empty plan for a market already staged. Found by the independent review of M24. Changed: an existing database is opened like the server's (`open_server_db`); a regression test stages a row and toggles.
- **A script's folder on `sys.path` is only a convenience.** True: running `ahsync_app/__main__.py` as a script put `ahsync_app/` first, and its `platform/` package shadowed the standard library's `platform`, which pywebview's Windows backend imports. Found by the independent review of M24. Changed: the script drops its own folder from `sys.path`; a test checks the stdlib module wins, and the `pythonw` login command was run for real.
- **A hidden window that cancels its close is invisible to Windows.** True: WinForms asks the same closing handler at sign-out, and a cancel there blocks it (`WM_QUERYENDSESSION` answered 0). Found by the independent review of M24, confirmed by sending the message. Changed: a second handler lets `WindowsShutDown` through (answered 1); the X button still hides.
- **2026-11-02 · A port that's in use fails to bind.** Every "port not available" path (setup mode's exit 2, the dashboard's log line) rested on it. True on Windows only for a plain socket: Python's HTTP servers set `SO_REUSEADDR`, and two of them listen on one port at once, the requests going to either. Found by the user at M24's manual check: with `python -m ahsync` still running, the app's setup window showed that dashboard's 404 for `/setup`. Changed: the dashboard binds with `SO_EXCLUSIVEADDRUSE` on Windows (FM57, SPEC §3.5).
- **2026-11-02 · Any HTTP call can go through `ApiClient`.** The plan sent GitHub's update check through it. True: it retries five times with a log line each and attaches the AHF key unless told not to, so FM52's one line and DR15's no-key rule would both have depended on remembering `auth=False` and living with retries. Found by Opus building M25. Changed: one plain GET through the transport (SPEC §3.7.8).
- **`UrllibTransport` turns every network failure into `TransportError`.** True for connect and timeout, not for a body cut off mid-read: `http.client.IncompleteRead` escaped. Found by Opus building M25's download (FM53). Changed: `HTTPException` is mapped too, with a test.
- **2026-11-02 · A verified download stays good until it is installed.** M25 kept `update.downloaded` until a later download failed. True: the channel can change, auto-update can be turned off and a Release can be withdrawn, so a beta could have waited on a stable install for M27 to install. Found by the independent review of M25. Changed: `engine/updates.ready` decides what waits, the updater removes the rest (DR30, SPEC §3.7.9).
- **2026-11-02 · A dmg can be stapled with its app's ticket.** DR18 stapled a dmg made from the notarized app. True: `stapler` looks a ticket up by the file's own code signature, and an unsigned, unsubmitted dmg has none, so the staple would fail every release. Found by Opus writing M26's signed build. Changed: the dmg is signed and notarized itself before stapling (DR18, SPEC §3.7.12).
- **2026-11-02 · A free instance lock means AHSync has exited.** The installer's quit (write the stop file, wait for the lock) assumed it. True: the shell releases the lock about a second before the process ends (measured on M26's packaged build), and Inno Setup could find `AHSync.exe` still in use. Found by Opus stopping the real build. Changed: the installer also waits up to 10 s for `AHSync.exe` to end (SPEC §3.7.12).
- **2026-11-02 · The from-source `sys.path` fix is harmless in a build.** `ahsync_app/__main__.py` drops its own folder from `sys.path` when run as a script. True: a PyInstaller build runs it as a script too, from its `_internal` folder, which holds the extension modules. Found by Opus writing the spec. Changed: the fix is skipped when `sys.frozen`.
- **2026-11-02 · `security import -P` is fine for the certificate password.** True: it puts the secret on a command line, which DR18 and the secrets rule forbid. Found by Opus writing M26. Changed: openssl reads it from the environment and re-encrypts with a throwaway password (SPEC §3.7.12).
- **2026-11-02 · A base64 secret arrives exactly as `base64` printed it.** `tools/build.py` decoded `MACOS_CERT_P12` strictly (`validate=True`), which rejects any newline. True: `base64` ends its output with a newline and a paste into GitHub's secret form keeps it (or the text is wrapped), so the first signed run on `main` failed "certificate invalid: MACOS_CERT_P12 is not base64". Found by the user's first manual signed run. Changed: whitespace is dropped before decoding (`decode_certificate`, DR18); INSTALL-side advice is to pipe the file through `tr -d '\n'` into `gh secret set`.
- **2026-11-02 · An imported Developer ID certificate is a usable identity.** True only when the keychain can chain it to Apple's root: the runner's keychains may lack the Developer ID Certification Authority (G2), and `security find-identity -v` silently drops an untrusted identity, so the first signed run imported "1 identity" and then found none. Found by the user's manual signed run. Changed: the G2 and G1 intermediates are committed under `packaging/macos/certs/` and imported into the temporary keychain, and the failure now logs each identity's kind, team and trust status (DR18, SPEC §3.7.12). UNVERIFIED as the cause until the next signed run: the log also showed an empty team, so the ID secrets are now trimmed too.
- **2026-11-02 · "No Developer ID identity" points at the chain or the team.** Assumed after the first failure (and fixed: the intermediates, the trimmed IDs). True: the `.p12` held Xcode's Apple Development certificate, which sits next to the Developer ID one in Keychain Access; the new identity log showed it (listed twice, once per `find-identity` section).
