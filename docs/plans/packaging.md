## 1. What is decided (do not re-litigate)

From the proposal's §0, the user's decisions of 2026-11-01:

1. **Audience: the user and a few friends.** First run: choose the WoW folder, enter the optional auctionhouse.fyi key, pick a market; clear instructions for the SmartScreen warning.
2. **Windows stays unsigned; the Mac app is signed and notarized** with the user's Developer ID Application certificate and the hardened runtime, using six GitHub repository secrets (`MACOS_CERT_P12`, `MACOS_CERT_PASSWORD`, `APPLE_TEAM_ID`, `NOTARY_KEY_ID`, `NOTARY_ISSUER_ID`, `NOTARY_KEY_P8`). Values never appear in the repo, logs, artifacts, chat or this plan.
3. **A tray / menu-bar icon** (Open dashboard, Status, Start at login, the update items, Quit). pystray, Pillow, pywebview (with pythonnet on Windows) and pyobjc are a **packaging-only exception**, in `ahsync_app/` only; `ahsync/` stays standard-library only (SPEC §5.0.1). *Amended at the plan review: the dashboard shows in the app's own window, not the browser; see below.*
4. **The repository is public, `ctng1213/WowAuction`** (already pushed). The update check and friends' downloads need no token.
5. **The user has an Apple Silicon Mac.** The macOS build is arm64 only; M26 is not done until the dmg has passed there.
6. **Start at login is ticked by default** on the setup page.
7. **Windows gets an Inno Setup installer** (per user, no admin); macOS stays a `.dmg`.
8. **One shared core, a thin layer per OS** (`ahsync_app/platform/`, ten members; "nine" was a miscount of the same list, corrected in M22); the convention test keeps OS branches inside it (DR16).
9. **Automatic updates are in this batch.** AHSync downloads, verifies (SHA256SUMS; on macOS also codesign and the Team ID) and installs new releases; `auto_update = false` means notify only.
10. **Creating a release is what signs.** A tag `v*` always signs and fails without the secrets; a push to `main` builds unsigned and, once a `v*` tag exists, runs a signing preflight; development branches and pull requests build unsigned; a manual run may ask for a full signed build without a release.
11. **Two release stages: beta, then GA.** Every tag publishes a signed GitHub pre-release; only beta-channel installs take it; the user tests it on the Windows PC and the Mac, then promotes the same Release (no rebuild) to the latest release.
12. **Versioning**: tags `vMAJOR.MINOR.PATCH`, first `v0.1.0`, no suffixes; `ahsync/version.py` holds `0.0.0` in source and the workflow writes the tag in; `EXPORT_VERSION` stays separate.
13. **Non-goals (v1)**: Windows code signing, rollback, mid-session installs, Linux, Intel macOS, a Settings page, a tray "Setup…" item, migrating a developer's `./data`, MSI or stores, more than one tester group.

- **The macOS bundle path is derived from the executable, never `/Applications` (M27; the user, 2026-11-01).** The swap, the restore and the writability check use the bundle three folders up from `exe`; FM54 and DR23 run with an app in `~/Applications`. §3.7.9, FM54, DR23, FM55.

**Decided during execution (Opus, M23).**

- **Setup mode is its own request handler**, `ahsync/web/setup_app.py` (`SetupApp`), served by `server.py`'s server class; the Host, Origin and token checks moved to module functions in `server.py` (`host_allowed`, `write_refusal`) that both use. `server.py` stays one responsibility and under its size.
- **`GET /api/app` comes from the shell** (`ahsync_app/app_info.py`) through `Runtime.app_info` into `DashboardApp.app_info`; `python -m ahsync` has no shell, so its dashboard answers `404` there, and the app card and the pill exist only in the app.
- **The setup page builds one string**: the market id preview "→ forever.<ruleset>.<faction>.us" from the dropdowns' codes, an identifier as config.toml holds it (no number, and the server checks the codes). The Check's pill reads "found" or "not found" from the answer's `ok`.
- **The key file is a new temp file created with mode 0600**, renamed over `api_key` and then `restrict_file`d: never readable by others, and a failed write keeps an earlier key file (the independent review's finding 3).
- **The key is checked**: one line of printable ASCII, no spaces, at most 256 characters, since it travels in an HTTP header whose error message would quote it (review finding 4; DR8 gains the case). **The folder** loses one pair of surrounding quotes and expands `~`; a relative folder fails the check.
- **The Status line `api_key_not_saved`** (topic `api_key_setup`, since FM25's `key_rejected` already owns `api_key`; review finding 5; warn): title "API key not saved", text "Enter it again, or set AUCTIONHOUSE_APIKEY."; cleared by a later successful setup and by any start that finds a key. Setup writes it by opening the database itself (no `run()` yet).
- **Setup's other answers**: a second save after a successful one is `409 already_set`; an unwritable `config.toml` is `500 config_not_written` with a message naming no path; in setup mode `/api/app`'s `addon` is "not installed yet" (muted) until the save installs it.
- **macOS Start at login is the plist file alone, no `launchctl` (the user, 2026-11-02, at M24; amends DR10, FM51).** `launchctl bootout` stops the job's process, which is AHSync itself after a login start, so turning the toggle off would have quit the app, and a self-heal's reload would too; `bootstrap` only started a second instance that exits at once. Enable writes the plist (temp file and rename; unchanged bytes are left alone), disable deletes it; launchd loads `~/Library/LaunchAgents` at each login. FM51's macOS half is a plist folder that can't be written. SPEC §3.7.5, DR10, FM51.
- **The app shell's dashboard paths are one `AppHooks` object (M24).** `web/server.py`'s `AppHooks(app_info, set_autostart)` replaces M23's `app_info` callable in `Runtime`, `serve_dashboard` and `DashboardApp`, so M25's update endpoints add fields instead of parameters; without it (`python -m ahsync`) the paths answer 404. The shell does the autostart write and keeps its Status line; the server only maps the outcome to HTTP.
- **The window's loop takes the main thread first (M24).** The shell is a `Session`: the window is created hidden on the setup page or the dashboard, `webview.start` blocks the main thread, and its start callback starts the tray and a worker that serves setup, installs the addon, self-heals start at login and runs `run()`. So setup shows in the window too. Quit sets the stop event; the worker, once `run()` returns, removes the tray and destroys the window.
- **pywebview's `destroy()` fires the `closing` event (M24, found end to end).** The close handler hid and cancelled every close, so Quit and the stop file left the app hanging; once Quit has begun the close goes through (`WindowState.quitting`). LESSONS.
- **The renderer decides the fallback (M24).** Anything but `edgechromium` (Windows) or `cocoa` (macOS) aborts the window through pywebview's `initialized` event and the browser takes over (FM56); MSHTML can't draw the dashboard. A WebView2 that fails inside its own start (logged by pywebview) is not detected; the lock keeps the profile from being in use twice, the one cause seen.
- **The webview keeps its profile in `<data>/webview` (M24)** (`private_mode=False`), so the dashboard's saved page and choices persist like they did in the browser.
- **Links that leave the dashboard rely on `target="_blank"` (M24).** pywebview hands new-window requests to the system browser; it has no hook to divert a plain link, so a test checks that every link built from a URL carries `target="_blank"`.
- **From source the login entry is `pythonw.exe <repo>/ahsync_app/__main__.py --autostart` (M24, found end to end).** `sys.executable` is Python, so the M23 entry would have started `python --autostart`. `ShellWorld.launch_args` carries the script (empty for a build); `__main__.py` puts the repository on `sys.path` when run as a script. The user's §9.3 check runs this way.
- **The tray in M24**: the hover has no sync time until M25 brings the Status facts to the shell ("AHSync <version>", from source "AHSync dev build"); the update items log that they come with M25 and M27; Status is disabled during setup; a tray that can't start is logged and AHSync runs on.
- **Status topics `autostart` and `window`** for `autostart_not_set` (with the failure's type name) and `window_unavailable`; a window that starts clears the latter. While `run()` holds the database the shell writes them over a plain connection (`open_server_db`: no migration, no staging cleanup, a 5 s lock wait); `Database.open` only before the first run (the independent review's blocker: `drop_staging` mid-refresh would have published an empty market).
- **Never block sign-out (M24, review finding 5, checked with `WM_QUERYENDSESSION`).** WinForms asks the closing handler when Windows ends the session, and the cancel to hide read as "AHSync is preventing sign-out". The WebView2 adapter adds a second `FormClosing` handler that lets a `WindowsShutDown` close through; the loop ends and AHSync stops. The X button still only hides.
- **Only a build refreshes the login entry at start (M24, review finding 6).** A source run (`launch_args` set) never self-heals, so it can't take over the installed app's entry; turning the toggle on from source still writes it, on purpose.
- **The worker survives the window and the tray (M24, review findings 3 and 4).** A failing open or menu rebuild is logged once per attempt and AHSync runs on; `run()` is always stopped and joined before the lock is released; once the window's loop has ended nothing destroys it again, and an error while it winds down is not a fallback.
- **The dashboard binds its port exclusively on Windows (M24, found at the user's manual check; FM57).** `SO_REUSEADDR` let the app's setup server share 8765 with a running `python -m ahsync`; now the second one fails to bind and says so. A packaged app with no console that can't bind setup's port still just exits (its message goes to the log only); M26 revisits that with the installer, which stops a running AHSync first.
- **Known limits recorded, not fixed (M24):** Ctrl-C in a windowed source run may not reach the main thread while the WinForms loop runs (use Quit); a Run value disabled in Task Manager (`StartupApproved`) still reads as on; the macOS tray probe (`AppKit`) and `pythonw.exe` are OS-shaped choices outside `platform/` that DR16's tokens don't catch, kept there because each is one line with no business rule.
- **Setup's start at login until M24**: the setup asks the platform, which raises "not built"; the shell logs it and carries on. `autostart.enabled` reads false until then. Any failure of a step after the save is logged and the hand-over goes ahead (review finding 1); the page restores its button when no answer comes.
- **Setup mode logs to `data/ahsync.log`** with the key in the redactor before any write, prints its URL, and ends on the stop file like `run()` (review findings 2 and 6).
- **The setup port is the default `dashboard_port` (8765)**, there being no config yet; `ShellWorld.setup_port` makes it injectable, so tests never bind a real AHSync's port.
