# Plan: the Blizzard source and the cloud market (M28–M35)

Written for: the Opus session that orchestrates this batch in Claude Code on this repo, delegating the tasks tagged **Sonnet** to Sonnet subagents and doing the tasks tagged **Opus** itself. The user's decisions were taken in conversation on 2026-11-06 (§1); the spec merge (SPEC §1, §2.4, §3.1, §3.6, §5.0, §6 items 23–25, §7 M28–M35; SCENARIOS BZ1–BZ24, FM67–FM72, SEC16–SEC17, S21–S23, D99–D100, AR9, SRC20; ARCHITECTURE §1, §2) is in the same commit as this plan. Nothing in §1 is open for redesign.

**What this batch is.** Market data moves from two community scan feeds (auctionhouse.fyi, AHledger) to Blizzard's own Forever auction API, read every hour by a cloud job that stores every raw snapshot and publishes the market analysis. AHSync stops analysing history and takes the published summary, keeping everything personal (characters, scans, mail, positions, the plan) local. Friends run the same app with only a URL.

## 1. What is decided (do not re-litigate)

The user's decisions of 2026-11-06:

1. **The source is Blizzard's Game Data API for WoW: Forever** (SPEC §2.4), found through community probing notes dated launch day (Nov 5). It is unofficial and undocumented; M28 records real responses before anything is built on the format.
2. **One market: PvE (ruleset 2 "Normal") Horde, US region**, AHSync's `forever.normal.horde.us`. The house id is verified by a marker auction (M28), never inferred: all 15 houses appear under every ruleset and one house answered identically under two.
3. **Roughly a snapshot an hour is the goal; the job runs a few times an hour to catch a new one.** Mechanism: EventBridge every 15 min, `If-Modified-Since`, snapshots stamped by Blizzard's `Last-Modified`, nothing written when unchanged.
4. **Raw snapshots go to S3 as Blizzard returned them**, gzipped, in an envelope with their provenance, kept forever. The raw is the source of truth; everything else can be rebuilt from it.
5. **The analysis runs the same code as the desktop.** `ahsync/engine/` and `ahsync/analysis/` are standard-library only and pure, so the Lambda imports them; no formula exists twice.
6. **The analyzer keeps a compact state and updates it each hour**, with a rebuild-from-raw command. Mechanism: AHSync's own SQLite schema (`history.db`) round-tripped through S3 (the planner's call, §1 "Decided at the merge").
7. **The maximum auction duration is 24 h** (2, 8, 24 h as SPEC §2.2 records; the user confirmed 2026-11-06). Lifetimes look back 24 h plus one snapshot, not 3 days.
8. **The summary carries the §3.3 primitives from the better source**, and the lifetime analysis is in this batch (M33). **Widened by the user 2026-11-06** to everything the raw lets us observe rather than estimate (SPEC §2.4 "Auction lifetimes"): each auction's posting window, duration and expiry window narrowed by its bands; partial fills as exact sales; sold or expired by where it vanished; sales credited to the vanish hour (so `sales_how` is measured); relists matched and *measured* before any subtraction; sell-through by price tier and window as an empirical `P` with a blend weight that rises with the sample; the undercut share measured; market-wide calibration (K8). Demand by price (elasticity) is a follow-up (SPEC §9). M33 begins by plotting the observed distributions from the raw collected by then and setting the tier edges, blend constants and band bounds from them, so no formula is designed blind.
9. **Low confidence for the first weeks is accepted.** The cloud history starts empty; windows reach "high" after 3 weeks per slot. AHF and AHledger stay on during the transition and go in M35.
10. **AHSync mainly takes the summaries and applies the personalization**: no local history analysis for a cloud market. The desktop runs recommendations, the portfolio, positions, the dashboard and the exports from the published document plus local state.
11. **Friends use the app too; the summaries are public**, as TradeSkillMaster publishes its pricing data: a private bucket, CloudFront serving the `intel/` prefix only, no AWS credential in any install. Raw snapshots and the state stay private.
12. **Item names and metadata**: use Blizzard's static item namespace if `static-forever-us` exists (probed in M28); otherwise ids are the keys and the addon layers names on as best effort. Consistency matters, names don't.
13. **AHF and AHledger are removed** in a final milestone (M35) after the cloud source has run cleanly for 14 days.
14. **Credentials**: the Blizzard client id and secret are in AWS Secrets Manager `wowauction/blizzard-api` (us-east-1, keys `client_id` and `client_secret`), created by the user 2026-11-06. The Lambda reads them at runtime; they appear in no environment text, log, raw file, fixture, commit or chat.
15. **Infrastructure as code**: AWS CDK in Python under `infra/`, region `us-east-1` (where the secret lives). The account id is not written in the repository (it is public).
16. **Failure alerts by email** (SNS), plus an AWS Budgets alarm.
17. **The cloud job runs locally, with the user's own credentials, from the same code** (the user, 2026-11-06). `python -m ahcloud collect|analyze|rebuild` runs the very `run()` the Lambda handler calls, against either a folder (`--store data/cloud`, a filesystem store behind the same adapter interface as S3: `raw/`, `state/`, `intel/` as sub-folders) or the real bucket (`--store s3://<bucket>`, through boto3's normal credential chain, so the user's AWS profile). Blizzard's client id and secret come from, in order: the environment (`BLIZZARD_CLIENT_ID`, `BLIZZARD_CLIENT_SECRET`), a key file `~/.ahsync/blizzard` (two lines, created with restricted permissions like the AHF key file, §3.7.4), or `--secret wowauction/blizzard-api` (the same Secrets Manager entry, read with the user's AWS credentials). Never a command-line value, never a file in the repo. A local `collect` writes the same envelope and key the Lambda would; a local `analyze` over the same raw publishes the byte-identical document (BZ31), so any cloud run can be reproduced on the user's machine from the raw objects alone (`--store s3://…` read-only for raw with `--out data/cloud` for the state and the document). `tools/record_blizzard.py` (M28) is the first user of the credential lookup.

**Decided at the design review (the user and the planner, 2026-11-06; the cadence split).** The user asked whether the hourly job did too much. It did: the first design recomputed every baseline 24 times a day, round-tripped the database every hour, and let the plan churn on hourly noise in the windows, against SPEC §3.1.1's own stability rule. Decisions:

- **Two cadences, one document** (SPEC §2.4 "Analyzer, two cadences, one document"). The analyzer function has a **daily mode** (09:00 UTC, the stack parameter `DAILY_HOUR_UTC`): the listing-driven ingest of the day's snapshots into `history.db`, `analyze_market`, the base document; and an **hourly mode** on each raw object: the newest two snapshots and the latest document, `with_scan` for the state fields, `last_hour` and the `recent` ring, every baseline copied through byte for byte, **no database**. Same document shape, one pointer, one reader; `built_ms` is the baselines' analysis time and `observations_until_ms` the newest snapshot applied. The two-document "pulse" form was considered and set aside as more than needed; it stays available later if an hourly event stream is wanted for notifications.
- **The desktop's scan cutoff moves to `observations_until_ms`** (BZ21): `with_scan` picked local scans "newer than `built_ms`", which would let a scan older than the hourly prices overwrite them.
- **Horizons and regimes are a milestone (M34)**: per item, 7 / 14 / 30 / 90-day rows (median, price slope, closes, sold per day, sales slope, listed per day, units on the AH, expired share) with "needs N more days" until a horizon is full, and a regime label from the 7-day row against the 30-day one. **The constants are set from two weeks of daily documents at M34's start** (the user, 2026-11-06), not now; the provisional values in SPEC §2.4 and BZ36 (±1% per day, 0.8×, 1.25×, 1.2×) are there so the rows have numbers to check.
- **Spikes are not a detector**; they are a notifications follow-up in SPEC §9, gated on M33's evidence: the plan already reacts to a price jump through the hourly prices, and whether a deviation is real often enough to be worth a message is what the lifetimes will show. A spike rule must agree with FM5's suspect rule (persistence, or units selling at the new level).
- **Status shows both ages** ("baselines built Fri 09:00 · prices to 15:02") and alerts separately on stale prices (3 h) and stale baselines (36 h) (S24).

**Decided at the architect review (the planner, 2026-11-06; independent review of the merge against the code).** Each corrects a mechanism above or fills a gap the review found; SPEC §2.4 and the scenario rows carry the same corrections. One **needs the user's OK**.

- **The analyzer keeps the compact snapshot store in S3 too** (`state/snapshots/<market>/blizzard/<at_ms>.json.gz` and its `index.json`, as `collect/snapshots.py` writes them), and each run downloads the window it needs: `recompute_id_volume` rebuilds a whole day from every snapshot since 6 h before it (`observations.py:84`), and lifetimes (M33) read 25 h. The raw envelope stays the source of truth; the compact store is a cache rebuilt by `rebuild`.
- **A run is driven by a listing, not by one event.** The S3 event (and an hourly schedule as a fallback, since async invokes throttled by reserved concurrency are dropped after 6 h) only triggers a run; the run lists `raw/<market>/` from the last ingested time, ingests every snapshot without a `scans` row in `at_ms` order, then publishes when the document's `observations_until_ms` is behind the database's `meta.last_ingested_at_ms`. That one rule covers a repeated event (BZ11: the `scans` row exists, nothing to do), a late snapshot (BZ13), a crash between the state upload and the pointer (BZ12: the next run republishes without re-ingesting) and a dropped event. Known limit, recorded: a snapshot that arrives after a newer one in the same clock hour replaces that hour's close with the older price (`local_scans.py:55`); with the collector fetching only the newest snapshot this cannot happen in practice.
- **`built_ms` is the newest ingested `at_ms`**, never the wall clock: `analyze_market(now_ms=at_ms)`, so a rebuild from raw gives the byte-identical document (FM72, §8.6), and ages are "age at build plus time since" on the desktop, as `recommend.portfolio.price_ages` already computes them.
- **The state file is uploaded as a `VACUUM INTO` copy** from a fresh directory per run, never the live WAL-mode file (writes could sit in `-wal`, and a warm Lambda's `/tmp` could replay a crashed run's journal). A cloud exception to §3.1.2's WAL rule, recorded there. The live key is written with a conditional `PutObject` (`If-Match` on the ETag the run downloaded), so a run that lost a race fails instead of overwriting; S3's PUT is atomic, so the temp-key-and-copy step goes. `rebuild` is an invocation of the analyzer function with a flag, so reserved concurrency serializes it too.
- **The cloud prunes order books to 2 days** (the desktop keeps 30): the analyzer needs only the newest book, the day's pairs and the 2-hour sales pairs, and 30 days of a 50k-entry house is tens of millions of `book_entries` rows. The database size is **measured in M28** from the recorded fixtures (entries per snapshot × items × hours), and the function's memory and ephemeral storage (up to 10 GB) are set from that, not guessed. Rationale recorded for the alternatives: EFS needs a VPC and a NAT gateway (about $32 a month) to reach Blizzard and Secrets Manager; DynamoDB means a second store.
- **The document key is its sha256**: `intel/<market>/<sha256>.json.gz`; a republish never overwrites a key CloudFront may still serve (FM71). The desktop polls and caches by `sha256`, not `built_ms`, and `publish_refresh` clears `IntelStore`'s parsed cache for the market (`intel/store.py:64` keys it on `(built, schema)` only).
- **The cloud document is staged inside the re-plan.** `replan_all` drops staging first and publishes with `with_intel=False` (`app/refresh.py:216-221`), which would discard a document staged before it; so `cloud_intel` hands the document to the re-plan, which stages it after `drop_staging` and publishes with a per-market `with_intel`. The full refresh skips `recompute_stale_volume` and `recompute_mail_volume` for a cloud market as well as the analysis (`refresh.py:248-254` read history).
- **The catalog field is `catalog`**, since `MarketIntelligence.items` is the per-item map (`intel/contract.py:102`).
- **Approved by the user 2026-11-06 (amends decision 12): the catalog must carry the vendor sell price and the item class, and vendor pricing is also local, adjusting as data comes in.** `analyze_item` prices the deposit from `vendor_sell` and gear windows from `item_class` (`analysis/market.py:216,228`), so "ids only" would silently change `sell_value` and windows. Cloud source: Blizzard's static namespace `static-forever-us`, which exists (M28; it has `sell_price` and `item_class`, no stack size). *The frozen AHF catalog planned as a fallback was dropped at M28 (below).* **Locally (M32)**: the addon's `itemNames` capture grows to `"quality,name,sellPrice,classId"` from `GetItemInfo` (the Adapter already reads `sellPrice`; the class id is `GetItemInfoInstant`'s, UNVERIFIED on Forever, checked through `wow-adapter`; A92), so every item a character has seen in game carries its vendor price and class on the desktop. The local catalog is the document's `catalog` with the addon's rows filling what it lacks, so an item the cloud could not price gets its deposit from the game's own value in the plan (BZ25), and the gap closes as characters see more items. The document's `sell_value` for such an item was built without a deposit; the plan prices it again locally from `post_price`, `chance` and the local deposit, and the item detail says "vendor price from the game".
- **The document carries the analysis settings** (`settings` in schema 10: the `MarketSettings` values it was built with), and a cloud market's plan uses them for the keys `MarketSettings` and `PlanSettings` share (`default_sell_prob`, `sell_window_hours`, `max_supply_share*`, `min_gear_units`, `max_trend_total`; `config.py:507,525`), with a Status note when the local config differs. The personal keys stay local.
- **Schema changes are additive, and the analyzer publishes two pointers during a transition**: `latest-<N>.json` and `latest-<N−1>.json` (the older rendered by `to_json(intel, schema=N−1)`, which drops fields added after N−1) for 14 days after a schema bump, so a friend's install on the older AHSync keeps working; AHSync fetches `latest-<INTEL_SCHEMA_VERSION>.json`. S22 remains for a schema older than N−1.
- **SEC16 is stricter**: the 64 MB bound applies to the decompressed body too (a small gzip can expand without limit); the key must match `^intel/<market>/[0-9a-f]{64}\.json\.gz$` exactly (no `..`, percent-encoding or absolute URL); redirects are not followed; the document's `market` must equal the configured market, because `stage_intel` writes whatever `intel.market` says.
- **SEC17 tests the bucket policy**, not the OAC: an origin access control cannot be scoped to a prefix by itself; the scope is the bucket policy's resource `arn:…/intel/*` with `AWS:SourceArn` = the distribution.
- **The Lambda asset includes `ahsync/data/`** (the bonus suffixes and suffix names `load_suffix_names` reads).
- **Noted, verified in M32**: catalog names reach generated Lua and HTML through the same export path AHF's names take today; the escaping is checked once more with a cloud-sourced name.

**Dependency review: `aws-cdk-lib` and `constructs` (Opus, M30, 2026-11-06; the `dependency-review` skill).**

1. **Need.** Decision 15 (infrastructure as code). The stack is a bucket with lifecycle rules, two functions, two schedules, an S3 notification with a dead-letter queue, a secret grant, CloudFront with origin access control and a bucket policy, an SNS topic, alarms and a budget: about a dozen resources with least-privilege policies between them. Hand-written CloudFormation could do it with no dependency, but the IAM policies, the OAC bucket-policy wiring and the asset upload are exactly where hand-written templates go wrong, and CDK's `assertions` module lets SEC17 test the template. The standard library has nothing comparable.
2. **Candidates.** CDK v2 in Python (proposed: same language as the repo, typed, testable with `aws_cdk.assertions`); AWS SAM (YAML, simpler for functions but weak for CloudFront, budgets and policy tests); raw CloudFormation (no dependency, no tests of intent). Terraform was not considered: a second toolchain and state backend for one stack.
3. **Maintenance.** Maintained by AWS; 2.275.0 is the current release, with releases about weekly; a large team, not one person's project. `constructs` is AWS's too.
4. **Compatibility.** Requires Python ≥ 3.10 (the repo is 3.12) and Node.js for the jsii runtime and the CLI: Node 24.14 and CDK CLI 2.1148 are already on the user's Mac. No overlap with any pinned package (`requirements-dev.txt` has pytest and coverage, `requirements-app.txt` the app shell's set). Not needed on Windows or in CI's `test` job unless `tests/infra/` runs there (decided below).
5. **Licence.** Apache-2.0 for the CDK packages and jsii; the tree is MIT (attrs, cattrs, typeguard, publication), BSD-3-Clause (python-dateutil), PSF-2.0 (typing_extensions), Apache-2.0 (tzdata). All permissive; nothing is distributed to users: it builds the infrastructure only.
6. **Security.** `pip-audit` against OSV: no known vulnerabilities in the resolved tree (13 packages). It reads no untrusted input at run time: it runs on the developer's machine to synthesize a template from our own code. The jsii runtime starts a Node process for each synth.
7. **Runtime cost.** 440 MB installed (mostly the bundled AWS CLI and Node proxy assets); imports in about 3 s; a synth takes seconds. None of it is in the app or the Lambda.
8. **Packaging.** Pure wheels, no native build. Never bundled: `tools/build_lambda.py` stages only `ahsync/` and `ahcloud/`, and AR9 checks that nothing outside `infra/` imports `aws_cdk`.
9. **Exit.** Contained in `infra/` (two or three modules). `cdk synth` emits plain CloudFormation, so leaving CDK means committing that template and deploying it directly; the deployed resources do not depend on CDK.

Pinned exactly with the resolved tree in `requirements-infra.txt`. **CI:** `tests/infra/` is skipped when `aws_cdk` is not importable, so the existing `test` job on Windows and macOS is unchanged; the stack tests run where the infra requirements are installed (the user's Mac, and later a CI job if wanted).

## 2. Working rules

CLAUDE.md "How work is run" applies. In short: one worktree per milestone; `tools/verify.ps1` (tests, invariants, the whole-plan snapshot byte-identical unless this plan says it moves) before a commit; one commit per verified milestone with the attribution trailer; the plan's §1 gains any decision made during execution; LESSONS gains any wrong assumption found; SPEC and SCENARIOS are updated in the same commit as the code that makes them true, and a milestone's "planned" becomes "built" with module names.

Specific to this batch:

- **Secrets.** The Blizzard client id and secret never enter the repo, a fixture, a log, a chat message or a command line. The recorder (`tools/record_blizzard.py`) reads `BLIZZARD_CLIENT_ID` and `BLIZZARD_CLIENT_SECRET` from the environment and strips the `Authorization` header and the token response from everything it saves. Fixtures are reviewed for a token before commit (`grep -i bearer`, `access_token`).
- **No AWS CLI through Bash.** The AWS MCP server's tools do reads and checks; `cdk deploy` runs from the user's shell with their credentials (M30, M31 deployment tasks are the user's or run with the user's explicit approval each time). Every change to the account goes through the stack; nothing is clicked together in the console.
- **Live checks are evidence.** A milestone that touches AWS is done only when the thing has been observed in the account: the raw objects at the expected cadence, the document read back through CloudFront, the alarm email received on an injected failure.
- **Cost is checked, not assumed.** M31 records the first week's cost from Cost Explorer against the estimate in SPEC §2.4; a miss over 2× is a finding.
- **Byte identity.** WP1's world is not a cloud market: it stays byte-identical through M28–M34. M35 moves it on purpose (labels only).

## 5. Risks and open questions

- **The API is unofficial.** Blizzard may rename, move or restrict it. The raw envelope keeps provenance so a change is diagnosable; FM33 refuses a changed format whole; the stale alarm says when data stops. The AHF and AHledger paths stay until M35 for that reason.
- **The house mapping may change after launch day** (the duplicate-content quirk). The marker-auction check is repeatable; a Status alert for "snapshot identical to another house" is not planned.
- **Cancellations count as sales** in every id-based method. Stated in SPEC; the confidence label is "est.". No fix exists with this API.
- **The SQLite round trip's size and time**: estimated in M28, measured in M31. If the database is still too big for the round trip after the 2-day book prune, the next step is uploading it gzipped (SQLite compresses 3–5×), then splitting `candles_h1` by month; EFS is the last resort because of the VPC and NAT cost.
- **Public summaries**: anyone with the URL can read them, by design (decision 11). If that changes, CloudFront signed URLs per install are the documented later option.
- **The analysis defaults are shared** (needs the user's OK above): a friend can't tune `default_sell_prob`; nobody did before either, but the knob existed.
